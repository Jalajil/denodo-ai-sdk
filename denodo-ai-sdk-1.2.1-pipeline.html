01 / Architecture

Two connected pipelines

The SDK uses retrieval-augmented generation to select relevant Denodo schemas. The LLM then generates Denodo Virtual Query Language (VQL), which is executed through the Data Marketplace. Metadata and optional sample rows help generate the query; execution supplies the answer data.

Where data lives: Denodo remains the query layer for enterprise data. The vector store contains indexed context, including optional sample rows. The configured LLM receives relevant schema context and, when generating an answer, a serialized subset of returned rows. A metadata-only question can finish without executing VQL.

02 / Runtime preparation

Configure services and initialize resources

1. Configuration

Create a virtual environment, install requirements.txt, and copy the SDK and chatbot .env.example templates to their runtime names. Set Denodo connectivity, LLM, embeddings, and vector-store configuration.

2. Start the application

run.py manages the selected SDK/chatbot processes. The API uses FastAPI; the sample chatbot is a separate web application. Remote MCP can be integrated into the API application.

3. Reuse resources

The API starts default resource initialization in a background task. state_manager provides reusable LLM and vector-store resources; request parameters select the provider/model combination.

This task cloned and inspected the source. Dependencies were not installed and no live Denodo or LLM requests were run.

03 / Preparation pipeline

Synchronize metadata before asking questions

1

Authenticate and authorize synchronization

GET /getMetadata fetches user permissions and checks access to vectorization endpoints. Supply at least one database or tag. The endpoint rejects unauthorized synchronization.

2

Choose scope and synchronization mode

Database and tag scopes are combined as a union for extraction. Excluded tags and view prefix/suffix filters narrow the selection. Full synchronization is the default; incremental mode activates change tracking and updates based on the saved timestamp.

3

Extract and represent the schema

Fetch metadata from the Data Marketplace in batches. Build schema JSON and textual documents containing the configured descriptions and associations. Optional sample data is collected separately; data-usage errors are included in the response.

4

Embed and store context

When insert=true, the selected embeddings provider and vector store persist schema context. Sample rows use ai_sdk_sample_data. With insert=false, return extracted metadata without inserting it. Embedding/insertion can run in parallel while Denodo requests remain sequential.

5

Keep the index current

Repeat synchronization when the semantic layer changes. A full insertion first clears the applicable existing scope. Incremental synchronization handles changes using the tracked state. No returned schema produces HTTP 204.

04 / Online request path

Inside /answerQuestion

1

Accept the request and resolve dependencies

GET and POST both call process_question. Parse authentication and forwarded custom headers, create a tracing session ID, and obtain the LLM, schema vector store, and sample-data vector store. Provider settings can be overridden per request.

2

Embed the question and fetch permissions concurrently

get_relevant_tables runs question embedding and the Data Marketplace permission request together. It builds the list of allowed view IDs and a map of view security restrictions.

3

Find relevant views and expand context

Search by question vector, database/tag scope, and allowed view IDs. Deduplicate view documents and perform extra searches when chunks reduce unique-view coverage. Add permitted associated views and explicitly requested views, subject to the total-view limit.

expand_set_views=false restricts the final set to use_views. In this implementation, initial embedding/search still occurs. No usable views causes a 404 with a contextual explanation.

4

Apply security to prompt context

Parse each view with its security information. Fetch relevant sample rows per view, but skip samples for views with row restrictions and remove restricted sample columns. The permission result also controls inclusion of Denodo LLM-function rules.

5

Choose data, metadata, or clarification

Combine configured base instructions with request instructions. The category LLM uses schema context and the selected mode to route the question. Ambiguity can produce a clarification response. Metadata mode produces a schema-based answer; mode=metadata, verbose=false returns metadata immediately without the category LLM call.

6

Generate a VQL query

process_sql_category calls query_to_vql. The prompt includes relevant schema, example values, the question, date, custom instructions, and selected VQL rules. Rule groups cover operations such as dates, aggregates, vectors, metric views, and JSON. Obligatory fields trigger stricter generation instructions.

Parse the generated VQL and explanation. Missing or NONE VQL returns a no-query response. Otherwise, continue to normalization and execution.

7

Execute, classify, and optionally repair

Send VQL and the row limit through the Data Marketplace execution API using the caller's authentication and custom headers. Classify the response as rows, empty, execution error, validation error, or connection error. The next section details the bounded repair loop.

8

Build the response

Serialize results as full, full_csv, llm, and llm_csv. “Full” means the rows returned by the limited execution, not the entire underlying dataset. With verbose=true, generate a natural-language answer and related questions; with plot=true, generate a graph. Eligible content-generation calls run concurrently.

Return the VQL in sql_query, explanation, execution result, related/used tables, optional graph, token counts, provider/model, and timing fields. The public API retains “SQL” field names even though it generates VQL.

05 / Version 1.2.1 behavior

The execution and repair loop

Before execution, normalize VQL and detect known LIMIT/subquery or LIMIT/OFFSET issues. A dedicated LLM rewrite can run at this stage independently of the request's execution-error fixer flag.

Execution outcomeNext action
Success with rowsReturn the successful query and result.
Success with zero rowsReturn empty by default. If enable_query_reviewer=true, ask the reviewer to keep the query or rewrite it.
Execution, validation, or connection errorIf enable_query_fixer=true, provide the error, query, and schema to a conversational fixer. It may produce a new query or give up.
Attempts exhausted / fixer gives upReturn a failure explanation and available query context. No successful result is invented.

The resolver fixes the chosen flow after the first outcome and permits at most two fix/review iterations. A static rewrite that seeds a subsequent fixer conversation counts as the first fixer attempt. This is not a blanket guarantee of exactly two total LLM calls or database executions.

Success and empty outcomes retain the resolved query. Failed runs return the resolver's stored original query, which may already include a static rewrite, together with the attempt explanations.

06 / Alternative entry points

Chatbot, MCP, and DeepQuery

Sample chatbot

A LangChain agent orchestrates tools and conversation history. Core tools are data_agent and metadata_search; DeepQuery and knowledge search are included when enabled.

The data tool calls /answerQuestion with mode=data and verbose=false. The outer chatbot uses the tool result to compose its streamed response. Each data-agent request must be self-contained.

Remote MCP

MCP tools expose data-agent and metadata-search capabilities. They extract caller authentication and invoke the same process_question implementation inside the SDK, then format tool responses.

This provides another client interface to the question pipeline.

Unstructured knowledge

The chatbot's knowledge_query searches a selected knowledge collection in a vector store and provides matching document text to the agent.

This is a separate document-retrieval path from generating VQL against Denodo views.

DeepQuery: a multi-step analysis path

Retrieve schema
→
Digest & plan
→
Tool-call loop
→
Analysis + trace

Optional report

/deepQuery retrieves relevant schema and initializes planning/execution LLMs. A schema digest informs the analysis agent. The agent plans and performs database-agent calls, optionally creating cohorts for comparisons, subject to loop and concurrent-tool limits.

The output includes an answer and deepquery_metadata containing the plan, tool calls, conversation, cohorts, and model/timing details. A separate /generateDeepQueryReport stage uses that metadata to generate visualizations and a styled HTML report.

08 / Worked illustration

“What were total sales by region last month?”

This example is conceptual, not a query run against your environment. Actual view names, date expressions, joins, and output depend on the indexed schema.

  1. Synchronize the relevant sales and region metadata, with descriptions and associations.
  2. The caller sends the question with a sales database scope and authentication.
  3. The SDK embeds the question, fetches permissions, and retrieves authorized sales/region views and applicable sample values.
  4. The category step selects data mode and relevant operations. If a business term is ambiguous, it may request clarification.
  5. The generation prompt produces VQL to filter last month's dates, group by region, and aggregate sales.
  6. Denodo executes the generated query. Errors can trigger repair; an empty result is returned unless review was enabled.
  7. The SDK returns rows and the query. With verbose mode enabled, the answer LLM summarizes the limited execution result. A chatbot tool call normally leaves that wording to the outer agent.

Illustrative POST body

{
  "question": "What were total sales by region last month?",
  "vdp_database_names": "sales_db",
  "mode": "data",
  "verbose": true,
  "plot": false,
  "vql_execute_rows_limit": 100,
  "enable_query_fixer": true,
  "enable_query_reviewer": false
}

Send to the configured SDK base URL plus /answerQuestion, with the appropriate Authorization header. Replace sales_db with an actual synchronized database.

09 / Dedicated SQL generation pipeline

How the LLM generates SQL, step by step

Natural-language question → authorized schema → LLM selection → generation prompt → SQL/VQL → execution feedback.

This is an additional pipeline focused on query generation. Denodo's target dialect is VQL; the SDK calls this its SQL category and returns the query in sql_query. The examples below illustrate the process rather than a live execution.

→

→
LLM call 2Generate one VQL query
→
Execute / repairDenodo feedback
Which path is shown? The standard /answerQuestion endpoint with mode="data". It normally makes one LLM call to select tables/rule categories and another to generate VQL, before any optional repair, answer, or plot calls. Data mode still performs the first LLM call. In mode="default", the SDK additionally starts metadata classification concurrently.
1

Receive a question and its constraints

The application supplies the question, authentication, database/tag scope, optional required views, and custom instructions. process_question obtains the configured LLM and vector-store resources. Base custom instructions are combined with request instructions before the LLM stages.

Output: question text, retrieval constraints, credentials, and model configuration.

2

Retrieve the schema the LLM needs

Embed the question while fetching the user's view permissions. Search indexed metadata within the permitted view IDs and requested scope, deduplicate matches, then expand with allowed associations and explicitly requested views. Retrieve relevant sample values where security permits.

The embedding model locates relevant context. It does not produce the SQL. The generation LLM receives the schema assembled from that context. With row restrictions, stored samples for that view are skipped; restricted sample columns are removed.

Output: candidate view schemas, relationships, sample values, and permissions. No usable views stops the request.

3

LLM call 1: select candidate tables and SQL capabilities

direct_sql_category receives the question, a readable selector schema, and custom instructions. Description-length limits reduce this selector context. Its prompt asks for candidate tables and operation tags, such as dates, arithmetic, window functions, JSON, or metric views. It can ask for clarification when ambiguity checking is enabled.

Illustrative selector output:

<query>
  <table>sales.orders</table>
  <table>sales.regions</table>
</query>

For a question involving dates, the output might also include <dates>1</dates>. These tags select prompt content; they are not the final query.

Output: selected view names and rule-selection tags, or a clarification response that stops generation.

4

Build the SQL-generation prompt in code

query_to_vql extracts the selected table tags, renders the relevant schema using SchemaCatalog, and includes sample values. Selector description trimming does not carry over to the full generation schema.

Prompt componentHow it guides SQL generation
QuestionDefines requested measures, dimensions, filters, and output.
Schema and samplesGround table/column names, types, join relationships, granularity, and value formats.
VQL restrictionsSupply core dialect rules plus selected operation-specific rule groups.
Custom instructionsCarry configured and request-specific requirements.
DateProvides temporal context. In this release, the date value is computed when the generation module is imported.
Generation-process instructionsAsk for output shape, granularity, conditions, and a single query. A stricter variant is inserted when the schema contains [OBLIGATORY] fields.

Vector and metric rules can also be enabled from the schema's field/view types. Denodo LLM-function rules require both a relevant selector tag and permission to use them.

Output: a fully populated QUERY_TO_VQL prompt.

5

LLM call 2: generate one SQL/VQL statement

The code invokes a LangChain sequence: PromptTemplate → llm.llm → StrOutputParser. The configured model generates query text from the assembled prompt. The template requires exact schema names, one VQL query, and a no-query result when the schema is insufficient or a required concrete filter value is missing.

The expected response has three tagged parts: a short query explanation in <thoughts>, filter/join information in <conditions>, and the actual statement in <vql>. These are the application's requested output fields.

Output: generated text containing VQL and explanation, plus measured token usage. Prompt instructions express intended behavior; execution is still needed to check whether the generated query works.

6

Extract the query and stop if none was generated

The SDK extracts the VQL and explanation tags and tolerates certain fenced-code responses. Empty or None VQL becomes GenerationStatus.NO_QUERY. A GeneratedQuery object otherwise carries VQL, explanation, token counts, and generated status.

Output: a structured query object. Tag parsing alone does not prove syntactic or business correctness.

7

Normalize, execute, and use errors as feedback

resolve_query normalizes VQL and checks known LIMIT-related issues. A dedicated static rewrite can run before execution. It then calls the Data Marketplace with the authenticated user's credentials and row limit.

If execution fails and the fixer is enabled, an additional LLM call receives the failed query, error, schema context, and VQL rules. Its replacement is executed again. For zero rows, the optional reviewer may keep or rewrite the query. The resolver uses a maximum of two fix/review iterations; a static rewrite can consume one fixer attempt when it seeds that flow.

Output: a successful query/result, legitimate empty result, or a terminal failure with attempt explanations. Successful execution does not by itself establish that the query captured the business intent correctly.

8

Return SQL and rows; optionally explain the result

The response includes sql_query, query_explanation, execution_result, token counts, and timing fields. With verbose=false and plot=false, the SQL path does not require a final prose/plot generation call. With verbose mode enabled, the answer LLM summarizes the execution result after query generation and execution.

A concrete example: question to generated SQL

Question: “Show total order amount by region.” Assume the indexed schema contains the following views, and that each region ID identifies one region:

sales.orders
  order_id     integer
  region_id    integer
  amount       decimal
  Granularity: one row per order

sales.regions
  region_id    integer
  region_name  text
  Granularity: one row per region

Association: orders.region_id = regions.region_id

Retrieval supplies these views. The selector identifies both as candidates. The generation prompt supplies their types, relationship, and granularity so the model can construct the join and aggregation. One possible query is:

SELECT
    r.region_name,
    SUM(o.amount) AS total_order_amount
FROM sales.orders o
JOIN sales.regions r
    ON o.region_id = r.region_id
GROUP BY r.region_name
ORDER BY total_order_amount DESC;
SQL clauseInformation used to generate it
FROM sales.ordersThe requested measure is order amount; schema identifies its source.
JOIN sales.regionsThe region label is in another view; the association supplies the join keys.
SUM(o.amount)“Total order amount” calls for summing order-level values.
GROUP BY r.region_name“By region” defines the requested grouping. This groups identical region labels together.
ORDER BY ... DESCAn illustrative presentation choice; it was not explicitly requested.

This schema and query are illustrative, not captured model output or an execution test. Actual generation depends on your semantic layer and model. For example, if distinct regions can share a name, grouping by region ID as well may be needed.
